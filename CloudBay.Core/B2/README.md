# Backblaze transport

`B2CloudStore` implements the B2 Native API v4 behind `ICloudStore`. Keep one store alive for the connected account. Call `Configure(uploadBytesPerSecond, downloadBytesPerSecond, connections)` for live transfer settings; zero means unlimited and connection counts range from 1 to 32.

Small files borrow exclusive upload URL/token sessions and return them to a reusable pool after a successful response. The shared `HttpClient` uses pooled HTTPS connections; successful and failed metadata responses are fully consumed before reuse. Uploads declare a fixed `Content-Length`, send a SHA1, and disable `Expect: 100-continue`. A rejecting upload endpoint is retired and the source is replayed against a fresh endpoint. Legacy non-seekable streams can replay in a RAM buffer capped at 4 MiB; larger streams require the replayable adapter. No upload payload is spooled to disk.

Files at least 64 MiB use multipart upload. Parts use the service's minimum/recommended sizes, include at least two parts, remain within the 10 TB whole-file, 10,000-part, and 5 GB-per-part limits, and stream through 64 KB buffers. All workers together obey the configured upload concurrency and aggregate bandwidth limit. The existing local-file API prepares whole-file and part checksums together and resumes its own durable journal. A lost finish acknowledgment is resolved by looking up the known file ID.

`B2TransferEndpoint` shares the transfer engine's plan, cursor, queue, receipts, and acknowledged checkpoints with local and OneDrive adapters. It uses independent immutable source range reads, bounded read-ahead, and `hex_digits_at_end` SHA1 trailers for both small files and multipart ranges; the declared wire length includes the 40 checksum bytes. This removes a full preparatory cloud read. Each acknowledged part saves its hash and exact byte count; restart reconciles B2 `b2_list_parts`, reuses acknowledged ranges, and rereads only a range whose acknowledgment was lost. Cancellation retains unfinished parts and recoverable progress. Expired/rejected upload endpoints are retired. An externally removed multipart session restarts only its unfinished file after confirming immutable absence. An uncertain small completion is searched by operation/source metadata and never blindly replayed.

Small upload content is checked against B2's provider SHA1. B2 whole-file SHA1 for large files is client metadata, so the adapter streams a completed multipart destination back through RAM before accepting verification. When the immutable source has no checksum, it also streams the original source to establish the comparison hash. These verification passes and provider metadata round trips are real overhead included in elapsed throughput. Move deletes the selected immutable B2 version only after verification, and refuses deletion if a newer current version appeared. Folder browsing uses B2's `/` delimiter; paged current-name discovery persists provider continuation cursors without scanning retained versions.

Full downloads verify whole-file SHA1 from the object's metadata, `X-Bz-Content-Sha1`, or `large_file_sha1` when available. Older external multipart objects without a checksum use authenticated HTTPS plus exact byte-length verification and raise a `Diagnostic` note. Range hydration requires an exact `206`, `Content-Range`, total size, and byte length. A full-file SHA1 cannot verify a partial byte range.

Retries are bounded to five attempts and use exponential backoff with jitter or `Retry-After` (bounded to two minutes). Expired account authorization is refreshed once across concurrent workers. Forbidden capability/cap failures are not retried. Exceptions never retain response messages, unknown error codes, authorization values, or unsafe inner exceptions. Network failures preserve the `HttpRequestException` type for offline status handling.

Metadata requests, acknowledgments, and error bodies have a 60-second bound. Downloads have a fresh 90-second inactivity bound for each network read. Uploads use a 90-second inactivity clock across socket writes and the final response headers, resetting after progress. Deliberate bandwidth throttling suspends that clock; an active large upload has no fixed whole-transfer deadline. Caller cancellation is preserved and is never retried as a timeout. Stalled response streams are disposed, failed upload endpoints are retired, and retries replay from the original source/destination position. The implementation follows [.NET response-header completion semantics](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.httpcompletionoption) and [`CancelAfter` reset behavior](https://learn.microsoft.com/en-us/dotnet/api/system.threading.cancellationtokensource.cancelafter).

Current listings use paginated version enumeration to preserve hide markers while selecting only the newest completed version for each key. Restores create new versions with server-side copy; large restores use ordered server-side copy parts. File names and timestamp metadata are interoperable with other B2 clients. Single and multi-bucket restricted application keys and name prefixes are enforced locally and by B2.

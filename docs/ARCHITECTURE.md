# CloudBay 2 architecture and acceptance criteria

CloudBay is a Windows desktop sync provider for Backblaze B2. The `legacy` branch preserves the mounted-drive folder migration application at `03656fb`. Main contains the new application, with independent cloud transport, reconciliation, Windows integration, and UI layers.

## Supported product behavior

- A private B2 bucket and a dedicated prefix hold cloud files and B2 version history.
- Windows Cloud Files registration provides Explorer navigation, status icons, download progress, pinned files, online-only files, and built-in availability commands.
- The process runs in the user's background session, survives closing its main window, starts at sign-in when selected, and provides a notification area activity flyout. A per-user mutex and restricted named pipe coordinate repeat launches and graceful shutdown.
- The UI uses WinUI 3 Mica Alt with Windows theme resources and keyboard-accessible settings.
- Backup supports Windows personal folders through documented Known Folder IDs and current policy capabilities, plus arbitrary personal data folders in their existing locations. Each custom folder is a separate native sync root, with its own durable baseline and cloud prefix.
- Windows personal folder backup uses an explicit Copy, Move, or No transfer review before changing the current user's real Windows folder mapping. Copies are verified and conflicts preserved. Moves remove exact originals after the mapping commits; unavailable or changed originals remain with a warning. The app checks live paths, policy, overlapping backup ownership, and the reviewed account. Interrupted mapping operations are recovered from an atomic intent journal.
- B2 transport keeps one HTTP pool alive. Reusable upload URLs are leased exclusively to workers and retained after successful uploads. Multipart files use streaming bounded memory and ordered, verified SHA1 parts. Aggregate concurrency and speed limits include multipart work.
- Activity publishes real per-file phases (queued, hashing, transferring, verifying, retrying, paused) with exact pending totals and a bounded 256-row presentation window. Stable UI rows retain their identity during progress updates. The tray shows live transfers before waiting counts and completed history.
- The sync engine obtains complete cloud and local snapshots before inferring deletions. It compares them to a durable SQLite baseline, preserves conflicts with atomic renames, retries failures, and leaves unsynced edits dirty. Large deletion batches require review of the exact pending set.
- Routine B2 reconciliation pages through current file names rather than retained version history. Every page and continuation cursor is validated, and an incomplete listing prevents reconciliation. A hidden name is absent from the complete current snapshot; explicit version browsing still uses the historical endpoint.
- Deletion uses B2 hide markers, preserving versions subject to the bucket owner's lifecycle policies. Locally removed cloud content is retained in Recovery. Empty directories have versioned zero-byte trailing-slash markers.
- Credentials are protected by current-user Windows DPAPI outside the repository. Diagnostics never contain application keys or authorization tokens.
- Account disconnect first hydrates and explicitly reverts cloud placeholders, restores backed-up Windows folder paths, and removes only the provider registrations. Local files and B2 versions remain.

## Windows integration decisions

Cloud Files uses `StorageProviderSyncRootManager`, `CfConnectSyncRoot`, `CfCreatePlaceholders`, `CfExecute`, `CfUpdatePlaceholder`, `CfConvertToPlaceholder`, pin/in-sync state APIs, and explicit placeholder reversion before unregistering. Native x64 layouts are verified against the installed Windows SDK `cfapi.h`. Hydration uses `FULL` with `ValidationRequired` and `AutoDehydrationAllowed`: Windows gates reads on provider validation and owns eviction of eligible clean, unpinned content. The app exposes the Windows Storage Sense settings page; it does not invent a competing cache quota or retention policy.

Storage Sense cloud-content eviction must be enabled by the user and is supported on the Windows system drive. Setting the provider's auto-dehydration modifier makes content eligible; it does not turn on Windows policy or override pinned files. On other supported NTFS drives, native on-demand hydration and explicit availability/free-space commands still work.

Personal folders use `SHGetKnownFolderPath`, `SHSetKnownFolderPath`, `IKnownFolder::GetRedirectionCapabilities`, and Explorer change notification. The original mapping is recorded before mutation; stopping backup also journals the chosen restore destination. Setup selects the current folder or one explicit external source. No transfer skips source inspection and hydration, retains existing files, and changes only the Windows location. Existing CloudBay or destination files can still be present; this choice does not empty a bucket. Policy-controlled locations remain blocked. Review caches bind choices to the account and root, and execution rechecks source fingerprints and the live Windows mapping.

Verified moves rehash source and destination ordinary content and named NTFS streams under held handles, check source identity and change metadata, and remove the exact source object with `SetFileInformationByHandle`. The file handles and ancestor guards prevent path substitution. Copy verification and mapping failure never remove originals; cancellation after mapping yields a retention warning. Empty source directories and their independent metadata are retained. Moving originals from another provider's Windows folder can propagate deletions through that provider. Moving from CloudBay uses normal version-preserving B2 deletion sync and retains its existing exact-batch safety review.

Folder changes have independent UI jobs. A shared dialog queue prevents overlapping modal choices, while the controller serializes reviewed mutations. Other folder switches remain available, queued jobs show their own status, and account connection changes wait until folder jobs finish. Stopping backup can release eligible downloaded CloudBay copies through the native dehydration guard; dirty or unverified files are retained.

Verified copying skips only Windows compatibility junctions identified by their native mount-point tag, Hidden/System attributes, and the Everyone deny-list ACL. It fingerprints their targets and permissions without traversing them. Ordinary junctions, linked roots, and destination links remain rejected. Folder customization files and the ReadOnly/Hidden/System attributes that activate them are preserved. Known-folder icons come from Windows shell definitions, while resident custom icon resources retain precedence; icon lookup does not recall online-only content or follow unknown links.

Attribute watchers observe both children and the root entry itself. Explicit Explorer PINNED/UNPINNED intent is handled without evicting dirty or incomplete content; cached UNPINNED content at startup stays eligible for Storage Sense. Pinned-folder hydration uses bounded parallel workers. A shared native hydration budget limits buffers across roots, while transport admission limits actual HTTP requests. A full response withholds its final aligned block until transport checks succeed; validation then checks the assembled Windows cache, including any retained prefix, before acknowledging clean remote data.

Windows Backup's own Microsoft-account backup UI is a Microsoft/OneDrive feature. CloudBay supplies real Windows folder locations and native Explorer integration; it does not claim to replace Microsoft's Windows Backup service, image an operating system, or back up locked live registry/application profile state. Windows, installed program locations, application profiles, volume roots, linked directory trees, nested provider roots, and incompatible volumes are rejected as sync roots. Supported personal Known Folders are queried from Windows; unavailable or policy-controlled folders are disabled with their reason.

## Storage and recovery

Per-user app data is `%LOCALAPPDATA%\CloudBay\Client`: atomic settings with previous copies, DPAPI credentials, bounded activity history, account/root-specific SQLite databases, backup operation intent, and Recovery. Unsynced or online-only files requiring atomic recovery on their own volume remain under the root's excluded `.cloudbay\Recovery`. Custom remote namespaces are reserved under `.cloudbay-backups/` beneath the account prefix and excluded from the main root so they are not downloaded twice.

The reconciliation baseline survives restarts. Watcher events wake the engine; a complete periodic scan recovers missed events. An inaccessible subtree is protected from upload, download, deletion inference, and directory-type replacement while readable siblings continue syncing. A failed root scan prevents all reconciliation. Real permission errors remain visible with actionable explanations and bounded repeat logging. Files are held against concurrent writes during hash/upload; late local edits during download are preserved before the verified remote data is installed. Placeholder identity contains the immutable B2 file version, so hydration fetches that exact object rather than a mutable filename.

Once B2 independently verifies an upload, the baseline records that immutable version before Windows metadata marking. A failed native status update leaves a durable pending-mark flag, so restart retries the Windows operation without creating a second upload. Those metadata operations use an exclusive read-data handle and retain read-only attributes; genuine access restrictions are not removed.

Import is an explicit copy workflow separate from continuous folder backup. Existing Windows cloud sources are discovered read-only from registered sync roots, environment paths, and bounded top-level profile candidates; detection never selects a source automatically. Local imports recheck the reviewed source fingerprint before writing and use the verified copy helper. Direct B2 imports snapshot immutable source versions, validate Windows path/case/hierarchy compatibility, and require a reviewed empty destination. Private bounded journals retain account/root identity, the immutable plan, and separate durable per-object receipts. Interrupted imports require explicit review or Continue; receipt verification checks operation identity, source version, destination, size, timestamp, and known checksum without reposting completed copies. Additional direct providers remain Coming soon.

An attribute-only native metadata probe checks dirty ranges without downloading cloud content. It detects local writes even when applications preserve file size and timestamps. Before marking an uploaded file clean, the provider verifies its SHA1 again under a referenced exclusive native handle, protecting a save that arrives between upload completion and native marking. Manual pause is inherited by new roots, and maintenance quiescence is retained while folder copying or unregister preparation runs.

## Transfer scheduling, restart and integrity

Intelligent scheduling uses CPU count and available process memory to select a bounded file budget (normally 4–8 workers per direction, 2 under low memory). Maximum throughput allows 16 per direction; Manual retains separate 1–16 upload/download choices. These are app-managed budgets, not a measured congestion-control algorithm. B2 request gates are shared across all roots and multipart workers. Whole-file hashing is limited to 1–2 workers, independent immutable-version metadata verification to eight, and native hydration buffers to 16 slots. Assembled native cache validation has one separate shared worker, avoiding a lock cycle when an ordinary file read already holds the hashing budget. Speed caps apply to aggregate payload traffic in each direction.

Upload workers feed a bounded acknowledgment channel (twice the file-worker budget); separate verifiers consume it. An uploaded file releases its network worker before verification, allowing the next queued file to use a pooled connection while earlier acknowledgments are checked. Backpressure bounds pending work. Native clean state and the sync baseline still advance only after verification. This removes an app-created gap between small files without claiming that B2's per-object latency or network variability disappears.

Rates use monotonic-clock payload measurements, a short smoothing window and idle expiry. Restored checkpoint bytes are a progress baseline rather than new traffic. Aggregate meters retain continuity across files in a batch; per-file meters stop during queueing, pause and verification. A native download stays visible as Verifying after transfer and enters completed history only when its native validation completes. A one-second pulse updates active views during a network stall without polling file contents or waking the UI while idle.

Multipart upload begins at 64 MiB. A single sequential preflight computes the whole-file and ordered part hashes under the shared hashing budget. Only the same read-only source stream and exact account/key/offset/size/mtime/part layout can consume that preparation. The durable private upload journal records identity and checksums, never credentials or contents. After restart, `b2_list_parts` supplies the authoritative confirmed parts; mismatched source or part metadata is rejected, and a changed source starts a new upload after safe cancellation of its prior managed version. Lost start/finish acknowledgments are recovered by the unique upload identity. Smaller files use a single atomic upload request and restart that file after interruption.

Every uploaded part includes its SHA1 for B2 to validate. Completed uploads are independently checked with `b2_get_file_info` before the sync baseline or native clean state advances. B2's whole-file SHA1 for multipart objects is client metadata, so this metadata check complements server-validated part hashes; it is not a second server-side whole-object rehash.

Ordinary downloaded files use version-bound private staging and parallel 8 MiB ranges (larger aligned ranges bound very large files to at most 10,000 chunks). Accepted chunks are flushed before atomic checkpoint publication, rehashed before restart reuse, and the final disk bytes are independently hashed before atomic installation. Small downloads avoid multipart scheduling overhead. Network retries continue from accepted bytes; destination-write and integrity failures do not replay bytes into a native sink. Incomplete or corrupt staged data never replaces an existing user file.

Native Cloud Files callbacks use exact immutable version IDs, validated range boundaries and lengths, and pooled TLS requests. An interrupted hydration can retain Windows' cached prefix across provider restart and fetch the missing remainder. Because a range response cannot independently prove a whole-object checksum, `RETRIEVE_DATA` reads the assembled cache from zero to EOF into a pooled 64 KiB buffer and compares its SHA1 with the immutable version's expected checksum. `ACK_DATA` releases clean remote data only after this check. No second private copy of the native cache is created. A mismatch requests one automatic full-cache `RESTART_HYDRATION`; a second mismatch rejects the request after discarding the rejected cache. Native modified ranges remain authoritative, so validation never discards unsent local edits to make them match an older cloud version.

Availability requires full on-disk coverage and coverage by validated or locally modified ranges. On-disk bytes awaiting acknowledgment are not treated as ready for recovery placement or icon reads. Queries use a fixed range buffer and a bounded loop; fragmented or unavailable metadata fails closed without recalling file content. A disconnected placeholder still uses its retained native range map even when Windows reports no placeholder-state flags.

Foreign legacy versions without a valid whole-file SHA1 have explicitly limited integrity proof: authenticated HTTPS, immutable version identity, and exact range/length checks. They are diagnosed as not checksum-verified. Windows handles native placeholder caching; private staged downloads have their own seven-day abandoned-part maintenance. Managed upload maintenance also runs periodically, skips active locks, and preserves checkpoints when remote cancellation cannot be confirmed.

## Release gates

1. Complete solution Release build with zero warnings and errors.
2. Transport tests with fake HTTP for session reuse, exclusivity, retries, auth renewal, range/hash integrity, multipart ordering/cancellation/finish recovery, and large legacy objects.
3. Reconciliation tests for complete-snapshot safety, dirty edits, concurrent saves, crash adoption, versioned deletion, directory markers, collisions, filters, pause/quiescence, and exact deletion review.
4. Real Windows Cloud Files tests in GUID-isolated user-profile roots: shell registration, native I/O hydration, pin/evict/rehydrate, dirty data protection, failed/canceled hydration, upload conversion, recovery, and data-preserving unregister.
5. Live tests against a bucket-restricted key, in a generated prefix only: small-file sessions, concurrent uploads, pagination, versions/restore/hide, full/ranged download, a >200 MB multipart file, canceled upload cleanup, native Explorer hydration, and controller multi-root lifecycle.
6. UI rendering across narrow/wide windows and light/dark themes; source uses actual native Mica Alt, which `RenderTargetBitmap` cannot capture from the desktop compositor.
7. Self-contained win-x64 publishing, installer/uninstaller path checks, Git whitespace verification, secret scan, and archive SHA256.

No finite test run proves correctness for every Windows installation, network interruption, or application workload. Public distribution additionally requires the publisher's signing certificate and testing on supported Windows release builds; the local artifact's actual verification scope is recorded in `VALIDATION.md`.

# CloudBay to CloudInlet: upgrades and optional migration

CloudBay users upgrade through the immutable **1.1.2** bridge before taking later CloudInlet releases. Published releases and tags are never rebuilt or replaced.

## Upgrade sequence

1. An original CloudBay installation uses its existing `TahsinFaiyaz30/CloudBay` schema-1 feed to install the frozen 1.1.2 package.
2. That package changes the product/executable to CloudInlet and retains the user's accounts, backup roots, Windows folder mappings, checkpoints, installer kind and build flavor.
3. Its CloudInlet updater reads `TahsinFaiyaz30/CloudInlet` and `updates-v2.json`. Subsequent releases use only canonical `CloudInlet-*` assets and schema 2.

The archived CloudBay repository keeps its seven existing bridge assets, including the byte-identical 1.1.2 aliases and schema-1 manifest. It needs no new releases or synchronization. The original source history remains in the canonical CloudInlet repository.

## Published bridge and current packages

CloudInlet 1.2.0 removed schema-1 update selection/downloads, legacy release-alias generation, the `CloudBay.exe` compatibility-launcher project, and obsolete executable/helper fallbacks from future installer payloads. Packaging rejects stale CloudBay binaries and legacy feed assets instead of silently shipping them. The bridge remains available as already-published bytes; it is not built by the new release pipeline.

Existing EXE/MSI installations normally upgrade **in their registered directory**, including a directory historically named `CloudBay` or `CloudBay Debug`. Fresh installs use `Programs\CloudInlet` or `Programs\CloudInlet Debug`. The frozen CloudInlet 1.1.2 worker verifies and reopens `CloudInlet.exe` at that original directory. A migration-capable worker must therefore be installed before a later update can offer installation relocation. The frozen bridge never relocates an installation.

Portable script installations also retain their validated registered directory. They refuse to take over managed EXE/MSI installations. An original CloudBay installation must take the published bridge first. Installers do not recursively remove historical directories or unknown files. An old EXE installation can retain an already-installed historical launcher until its normal uninstaller removes its owned files; future packages contain no such launcher.

Published 1.1.2 and 1.2.0 bytes and tags remain unchanged. The migration work below is unreleased; publishing it requires a new version and the relevant acceptance checks. `scripts/test-installers.ps1` exercises the frozen 1.1.2 installer/worker to a synthetic newer version, then a second update using the current worker, for both EXE and MSI.

## Opt-in migration in development

Startup inventories exact saved legacy locations before opening the transfer controller. Settings > Updates also offers **Review migration**. The review displays current and proposed locations, starts with no items selected, and provides Select all available and Deselect all. A second confirmation records the selected plan. Declining an item preserves that location and does not prevent future updates.

Application data and eligible local sync/backup folders have coupled migration adapters. Application-data migration preserves settings, DPAPI-protected accounts, databases and recovery metadata, then commits protected location routing. Folder migration checks saved references, hydrates and verifies registered placeholders before unregistering, moves the original directory without merging or overwriting, updates matching backup/exclusion/history references and Windows folder mappings, and verifies the new registration. It preserves each backup's account and manifest identity. Nested roots, conflicting destinations and unresolved active work stop that item for review.

Progress and recovery are item-specific. The WinUI dialog shows the current operation, measured progress when available, saved activity and a visible failure reason. Temporary errors receive bounded retries. An interrupted or failed item can be retried or reverted where its saved recovery state permits it; completed items are never reverted as part of another item's recovery. Startup keeps transfers stopped until every selected item is verified, reverted or blocked before mutation. Recovery records live outside the directories being moved.

An owned Files On-Demand registration can also be migrated while retaining the existing folder. This adapter verifies the original directory and account identity, downloads and verifies online-only files, preserves the manifest, changes only the selected root binding, and registers the same folder under CloudInlet. Its protected receipt supports retry or restoration of an incomplete registration. Unrelated registrations and changed settings stop the operation without being overwritten. Store application and startup-task identifiers remain stable package contracts.

Installation folders, distribution registration, installer ownership and shortcuts are one coupled choice. The current MSI worker can request a strictly newer MSI update with relocation; ordinary or declined updates retain their directory. The EXE worker first completes and verifies the ordinary update at the existing location, then uses that installation's own uninstaller and the same verified package to relocate a selected `CloudBay`/`CloudBay Debug` folder. Personal files outside installer ownership remain in the original folder. An EXE installation in a custom or already canonical folder can instead migrate its old registration while retaining the exact original directory object. The protected receipt distinguishes these operations and rejects a changed mode or directory. Repair, uninstall and restart-required outcomes are separate acceptance checks.

EXE relocation retains the verified package, recovery helper and protected state outside the installation. A separate Fluent recovery window must authenticate readiness before uninstall begins. The update progress window hands over to that window; both can briefly hold read leases on the runtime while cleanup remains excluded. Retry resumes the saved step, and Restore original location preserves the completed application update. Completed relocation cannot be reverted by retrying another step. Normal app startup reopens pending recovery before opening the profile. Interrupted preparation is not published as a pending migration until its package and receipt are durable.

The EXE continuation is saved before its ordinary in-place update, so an initial update that requires restart does not lose the selected migration when the installed version advances. Every native update, uninstall and reinstall records its operation and Windows boot identity before launch, then durably records its exit. A requested restart or unknown native outcome blocks further mutations, completion and opening the app in the same boot. After restart, recovery verifies an already installed target instead of requiring another newer package. The recovery window explains the pending restart and never restarts Windows automatically; an active installer continues showing progress rather than prompting a reboot. Simulated boot changes exercise this policy, while an actual reboot remains a separate acceptance gate.

For EXE registration migration in the same folder, cancelling before native uninstall retains the original registration. After uninstall, restoring the updated application in that folder also completes its CloudInlet registration, so recovery reports **Completed**, never a false reversal. The window explains this before restoration. The verified native uninstaller owns removal of old package files, including obsolete bridge components. After its self-delete finishes, every surviving file is checked against the original inventory and durably recorded before setup runs; those files must still match after installation. The original directory is pinned and its native identity rechecked before setup, so recovery cannot overwrite a replacement directory.

Cloud-prefix migration remains unavailable pending live-provider acceptance. Its implementation preserves original version history, content timestamps, metadata and explicit supported encryption settings, with no payload staging on disk. Protected journals store immutable snapshots and incremental version/part changes, verify their committed chain on reopening, and reject corrupt or missing committed records. The review requires explicit confirmation that other cloud writers are paused. The provisioned test key still lacks retention and legal-hold read capabilities; unknown protection must not be treated as disabled, and no existing cloud history may be mutated to bypass that gate.

The MSI migration handoff opens a separate Fluent progress window before the main application closes. Its verified runtime is staged outside both the installation and private-state folders. The window reads request-bound, DPAPI-protected progress; an explicit committed handoff is required before the helper can start installation. A canceled or incomplete handoff leaves the existing installation in place. After Windows Installer succeeds, progress-storage or app-relaunch errors remain visible without undoing an independently verified migration. Closing the progress window does not terminate the installer. Cleanup removes only inactive, byte-verified runtime files and retains small recovery/ownership records.

An MSI restart-required result remains incomplete and visible until another Windows boot and successful verification of the new installation, canonical registration, exact directory identity and retirement of old installer-owned files. The helper saves authenticated recovery evidence outside private state and the update cache before running the installer. Startup retries verification without rerunning an installer. Plain result JSON never authorizes completion. Pending recovery blocks another installation, automatic or manual package cleanup, and new profile-migration reviews. Completed migrations are not reverted. Isolated tests cover simulated boot boundaries; an actual reboot remains a separate acceptance gate.

Store migration additionally requires explicit virtualization exclusions for both private-state locations and the migration-routing directory. Older packages without those scopes retain their original state location. Candidate-package lifecycle checks cover preservation across removal/reinstallation; they do not imply Microsoft certification or live-provider acceptance.

## Durable identity and user data

DPAPI entropy, SQLite and `.cloudbay` recovery formats, pipes/mutexes, EXE AppIds, MSI UpgradeCodes, Store application ID `CloudBay` and startup task `CloudBayStartup` remain stable contracts. Legacy data paths, Cloud Files root IDs and `Software\CloudBay\Distribution` remain supported when their corresponding migration is declined or unavailable. Only a verified coupled adapter may replace the applicable path or registration; a branding search-and-replace is never a migration.

Accounts and unchecked backup paths are preserved. Cloud prefixes remain unchanged until the cloud migration adapter passes its separate all-version, metadata, retention, concurrency and interruption checks. Existing deterministic keep-both receipts remain readable; new names use CloudInlet. Updater-cache ownership and safe cleanup of historical cached packages also remain stable.

The OneDrive public application registration and legacy environment fallbacks remain unchanged so existing deployments and saved refresh tokens continue working. The small startup-record recovery routine also remains part of Windows-state preservation: it recognizes only this installation's old Run entry and carries Windows' disabled-startup choice forward without shipping an old executable. The rename does not change transfer scheduling, integrity checks or bounded-RAM cloud-to-cloud payload handling.

Live provider tests require explicitly provisioned isolated credentials and destinations. Ordinary release validation excludes that category and does not count it as passed.

See [Migration acceptance](MIGRATION_ACCEPTANCE.md) for the opt-in, scoped B2 history test, its read-only preflight and the separate Windows/live recovery gates. An inconclusive preflight is not a passed live migration.

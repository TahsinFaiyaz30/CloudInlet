Use the setup evidence's three **different** identities. `vmId` is the Hyper-V object identity; `firmwareUuid` is the guest-visible SMBIOS UUID, obtained from the provisioned VM's BIOS GUID. ## Run the known-folder restart case

The commands below execute inside the guest only. Replace the assembly path with the copied complete output. The runner does not build, install, shut down, restart or delete the VM.

```powershell
$tests = 'C:\AcceptanceTools\tests\CloudInlet.Tests.dll'
pwsh -NoProfile -File .\test-migration-guest-folders.ps1 -Stage Prepare -TestAssembly $tests -ConfirmDisposableGuest
pwsh -NoProfile -File .\test-migration-guest-folders.ps1 -Stage VerifyBeforeRestart -TestAssembly $tests -ConfirmDisposableGuest
```

`Prepare` requires Documents, Pictures and Music to be at their native default profile paths. Its read-only preflight allows empty native subfolders, small hidden/system `desktop.ini` metadata, and Windows compatibility junctions recognized by the production reparse-tag and deny-enumeration ACL checks. It never follows those junctions. Unexpected files, ordinary links and oversized inventories are rejected and retained. It never moves or clears pre-existing content to satisfy the preflight. It records the original Shell paths and generated fixture hashes, then uses production `KnownFolderBackup` review/copy behavior to enable three backups under an isolated CloudBay root. An unselected Downloads fixture stays in its original location. The production `ClientFolderMigration` and `MigrationSession` then run: an independent selection completes first, and an injected exception interrupts the folder item immediately after its **first real Shell mapping write**. The failure is visible and durable. File bytes, original directory identity, partial mappings, old settings and the completed selection are checked.

`VerifyBeforeRestart` reopens the protected evidence on the original boot and validates the precise partial state. It changes no Shell mappings. After that stage passes, gracefully restart **only the dedicated guest**, then sign back into the same test account. Do not use a checkpoint restore as a substitute for this restart.

```powershell
pwsh -NoProfile -File .\test-migration-guest-folders.ps1 -Stage VerifyAfterRestart -TestAssembly $tests -ConfirmDisposableGuest
```

`VerifyAfterRestart` requires the production `InstallerMigrationRecovery.CurrentBootIdentity()` value to differ while the saved receipt remains unchanged. Independently, Windows' last boot time and Kernel-General event 12 record/time must advance. The test then reopens the actual folder and session journals and invokes Retry. It verifies all three real Shell mappings, updated backup references, retained directory identity and payload hashes. The already completed selection stays completed; completed selections cannot be reverted. It records real reboot verification only if the entire stage passes.

After collecting the evidence, restore only the verified fixture mappings through production backup restore behavior:

```powershell
pwsh -NoProfile -File .\test-migration-guest-folders.ps1 -Stage RestoreMappings -TestAssembly $tests -ConfirmDisposableGuest
```

Restoration uses copy mode and retains both fixture copies, all protected receipts and logs. It checks the expected current mapping before changing it and refuses a third-party location. The stage can resume if some mappings were already restored. It does not delete files, unregister arbitrary integrations, clean a failed migration, or discard the VM. Export evidence before separately disposing of the dedicated guest.

## Evidence and remaining acceptance

### Recovery with a corrected test runtime

An existing failed scenario may be recovered with a separately staged corrected runtime using the explicit `RevertPriorRuntime` and `RestorePriorRuntime` stages. Both require the same nonempty `-ScenarioId`, the immutable previous harness's `-PriorRuntimeInventory` path, and its separately reviewed `-PriorRuntimeInventorySha256`. The test matches that inventory to the original runtime hashes in the protected boundary; it does not replace those hashes or overwrite the older binaries. Ordinary stages still require identical runtime hashes. Reports identify the changed runtime, prior inventory digest and recovery stage, and never count this as passing the earlier failed reboot test. Preserve every original report, receipt and fixture before starting. After recovery, a fresh scenario is still required to accept the corrected runtime's full before/restart/after path.

Post-restart recovery permits Windows to have recreated a previous mapped folder only when production's own bounded check accepts it: ordinary mapped directories and small hidden/system `desktop.ini` files, with no links, named streams, online-only entries, unexpected directories or user files. Production preserves the entire recreated directory as a separately journaled `CloudInlet recovered folder ...` sibling and verifies its identity and metadata before continuing. It never merges or deletes that folder. Any unexpected or concurrently added content stops recovery visibly and remains available. Test preparation and the before-restart check still require the precise initial partial state.

If Windows denies that preservation rename, recovery probes only the verified metadata entries for a sharing conflict, without reading payloads or modifying anything. A confirmed sharing violation uses the existing bounded, cancellation-aware session retries with visible progress. Permission denials and unclassified failures retain both locations and report the recovery paths; recovery never changes permissions or terminates another application. The guest assertion includes the saved migration error so a failed stage exposes the underlying cause.

The scenario writes under `C:\CloudInletMigrationLab\known-folders-<fixtureId>`. Retain `boundary.dpapi`, production receipts, `session.json`, durable `progress.jsonl`, every uniquely named `stage-*.json`, and the runner's TRX result directory. Failures retain all state; they never turn into a silent cleanup or a false success. A phase left at `Preparing` needs inspection or disposal of this isolated guest, not a blind rerun. The runner also refuses an inconclusive/skipped test result as a pass.

If an inspected failure happened during preflight, before any boundary receipt, fixture payload or Shell change, a corrected harness may use an explicitly reviewed fresh `-ScenarioId <GUID>` under the same authenticated guest enrollment. This creates `known-folders-<fixtureId>-<scenarioId>` and preserves the original failure directory. Supply the same scenario ID and identical verified harness to every later stage; paths and the plan fingerprint bind recovery to that scenario. This option is not a retry or cleanup mechanism for a partially migrated case. Never overwrite the original setup receipt or harness to deploy the correction; stage and verify a separate complete harness directory.

This staged folder test uses real Known Folder APIs and production migration code. It does **not** by itself exercise the WinUI review/observer, sign-in recovery startup, an external writer changing a real Shell mapping, or a native EXE/MSI installer returning 3010. Its exception is an explicit test injection, not evidence of an installer or network failure. The separate EXE WinUI restart, controlled unknown-outcome recovery, EXE post-recovery lifecycle, synthetic native MSI restart and autonomous MSI lifecycle evidence are described above. Natural pending file replacement remains a separate gate in the ignored `artifacts/migration-review/REBOOT-LAB-PLAN-2026-10-17.md`; do not infer it from a passing folder restart test. Capture the real folder review and Explorer location separately when those guest flows are run.
